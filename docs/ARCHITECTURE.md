# MATRIX — خطة إعادة الهيكلة لوحدات مستقلة (Modules)

**أُنشئ هذا الملف بتاريخ 2026-09-16 بقرار مباشر من أنس**: تفكيك MATRIX تدريجياً لوحدات (modules)
مستقلة قابلة للتطوير بالتوازي، مع طبقة تنسيق واضحة بينها — بحيث مستقبلاً أي طلب تعديل/تطوير على
جزء محدد يمكن تنفيذه داخل وحدته فقط دون لمس بقية التطبيق. **القرار مبني على ستة تقارير تصميم أنتجها
ستة وكلاء بحث متوازين (بلا كتابة على القرص)، راجعوا الكود الفعلي فعلياً قبل الاقتراح — لا تخمين.**

## المبدأ الحاكم للهجرة (اتفق عليه الستة وكلاء بشكل مستقل تماماً، بلا تنسيق مسبق بينهم)

**لا إعادة بناء دفعة واحدة (no big-bang rewrite). التطبيق يبقى يعمل طوال كل خطوة.** كل خطوة هجرة:
(أ) لا تغيّر أي سلوك ظاهر للمستخدم، (ب) قابلة للتنفيذ والتحقّق منها منفردة، (ج) قابلة للتراجع عنها
منفردة لو ظهرت مشكلة. الوحدات تُبنى بالإضافة أولاً (additive) — الكود القديم يستمر بالعمل بمسار قديم
مؤقت (shim/re-export) بينما يُبنى المسار الجديد بجانبه، ثم يُحذَف القديم بعد التأكد.

**⚠️ قرار حاسم من وكيل تصميم محرك الشارت، يُطبَّق حرفياً**: منطق الرسم الأساسي والتحريك/التكبير
(pan/zoom) داخل `MatrixChart.tsx` هو أخطر وأهم ملف بالتطبيق بلا أي تغطية اختبارات ظاهرة — **لا يُلمَس
إطلاقاً قبل إطلاق الأسبوعين**. فقط الخطوات الإضافية الآمنة ميكانيكياً (تقسيم math.ts، سجل مؤشرات
إضافي) تُنفَّذ الآن؛ إعادة هيكلة MatrixChart.tsx نفسه تُؤجَّل لما بعد الإطلاق.

```

    drawing-tools/      # أدوات الرسم (trend/ray/hline/…)، drawingStore.ts

    account/            # AuthContext, AccountScreen (هوية فقط — لا شبكة/عمولات)
    academy/            # CoursesScreen, LectureClassroom, academyChart.ts, academy.ts
    tools-panels/       # (حُذف 2026-09-25: registry.ts لم يستورده أحد قط — يُستعاد من 3c27653 عند النقل الفعلي)
                        # يحل تكرار المشكلة بين MatrixBottomDock.tsx وToolsScreen.tsx
  # يبقى مشتركاً خارج أي وحدة (طبقة أساس/منصّة يعتمد عليها الجميع):
  api.ts (النقل HTTP الخام فقط)، i18n/، theme.ts، notifications.ts

backend/
  app.py               # كان main.py — فقط FastAPI()+lifespan+include_router
  core/
    auth.py             # _auth_user + جلسات — يُستخرَج أولاً، كل شيء يعتمد عليه
    db_conn.py           # _conn()/init_db() — نقطة اتصال SQLite الوحيدة، لا فروع أخرى مطلقاً
  routers/               # APIRouter واحد لكل نطاق (auth/market/alerts/social/academy/…)
  repositories/          # db.py مقسَّم بنفس تجميع النطاقات الموجود فعلاً
  services/               # الملفات المنفصلة أصلاً (twelve_data.py، academy_data.py…) تُنقَل هنا فقط
```

## طبقة التنسيق بين الوحدات (ما طلبه أنس تحديداً)

1. **حاجز الاستيراد**: كل وحدة تُصدِّر واجهة عامة واحدة فقط عبر `index.ts` (مثال: وحدة الحساب تُصدِّر
   `useAuth`/`AuthProvider`/`AccountTab` فقط). أي وحدة أخرى تستورد من الحاجز `../modules/x` **فقط**،
   ممنوع الوصول لملفات داخلية لوحدة أخرى مباشرة. هذا هو الحد الفاصل الذي يمنع التعارضات.
2. **بنية تحتية مشتركة (Platform)**: `api.ts` (نقل HTTP خام فقط، لا منطق نطاق)، `i18n/`، `theme.ts`،
   `notifications.ts` تبقى خارج أي وحدة لأنها يعتمد عليها الجميع — تغييرها يحتاج مراجعة أوسع، عكس
   تغيير داخل وحدة واحدة.
3. **نمط "التسجيل الذاتي" لواجهات المستخدم المشتركة** (اقتراح وحدة الأدوات، قابل للتعميم): بدل أن
   يستورد `MatrixBottomDock.tsx` كل لوحة يدوياً (نقطة اختناق حالية مؤكَّدة)، كل وحدة "تُسجِّل" مكوّنها
   عبر `registerToolPanel({...})` عند التحميل. الملف المضيف لا يتغيّر إطلاقاً عند إضافة/حذف وحدة.
4. **الباك-إند**: `core/auth.py` و`core/db_conn.py` نقطتا التنسيق الإلزاميتان الوحيدتان — كل Router
   يعتمد عليهما، ولا يُنشئ أي repository اتصال SQLite خاصاً به (خطر تعارض كتابة حقيقي بSQLite).

## خطة الهجرة الفورية الآمنة (تُنفَّذ الآن، لا تنتظر ما بعد الإطلاق — صفر خطر على الميزات الحالية)

هذه الخطوات فقط مؤهَّلة للتنفيذ الآن قبل الإطلاق (نقل ميكانيكي بلا تغيير سلوك، كل خطوة مُختبَرة
بقراءة الملف كاملاً بعد النقل + تحقّق حجم postwrite كالمعتاد):

1. الباك-إند: استخراج `_auth_user` + دوال الجلسة إلى `backend/core/auth.py`، مع إبقاء `main.py`
   يستورد منه (لا تغيير بمسارات API إطلاقاً).
2. الباك-إند: استخراج `_conn()`/`init_db()` إلى `backend/core/db_conn.py`، كل شيء آخر يستوردها من
   هناك فقط.
3. ✅ **منجَز (2026-09-16 مساءً)**: الواجهة — تقسيم `math.ts` (كان ٥٨٩٤ سطراً/١٦٣ تصريحاً) إلى
   `chart/indicators/{utils,moving-averages,trend,momentum,volatility,volume,price-transform}.ts`
   + حاجز `chart/indicators/index.ts`. `math.ts` نفسه أصبح ملف تمرير سطر واحد
   (`export * from './indicators'`) بدل تحويله لمجلد — يتجنّب حذف/تعارض تسمية، ونفس مسار
   الاستيراد `'../chart/math'` يستمر يعمل بلا أي تغيير بأي مستهلك (MatrixChart.tsx وغيره).
   التنفيذ كان استخراجاً نصياً برمجياً (سكربت بايثون يقصّ كل دالة بحدودها الحرفية من الملف
   الأصلي) لا كتابة يدوية — تحقّق تلقائي: إعادة التجميع بالترتيب الأصلي طابقت الملف الأصلي
   حرفياً بايت-لبايت، وكل تصريح وُضع في ملف واحد بالضبط بلا فقدان أو تكرار. مساعدات المتوسطات
   المتحركة الداخلية (sma/ema/wma/…) كانت غير مُصدَّرة بالأصل — صُدِّرت الآن لأن الاستخدام عبر
   ملفات. تبعيات متبادلة حقيقية بين العائلات (مثال: `trend.ts` يستخدم `computeAtr` من
   `volatility.ts`) عولجت باستيراد صريح لكل اسم من ملفه الفعلي (لا استيراد دائري من الحاجز).
   **لم يُشغَّل tsc/بناء فعلي بعد** (لا صلاحية طرفية على الجهاز حالياً) — التحقّق الحالي نصّي/بنيوي
   فقط؛ أول تشغيل للتطبيق بعد هذا التغيير يستحق فحصاً بصرياً سريعاً للشارت والمؤشرات.
4. الواجهة: إنشاء `modules/tools-panels/registry.ts` (كود إضافي جديد فقط، ميت حتى يُستخدَم) تمهيداً
   لنقل الألواح الثمانية لاحقاً واحداً تلو الآخر. (حُذف 2026-09-25 بعد بقائه غير مستورد؛ `git show 3c27653` يعيده.)
5. **اكتشاف جانبي أثناء التصميم يستحق إصلاحاً فورياً منفصلاً**: مدرسة "أساسيات التداول للمبتدئين"
   موجودة فعلاً بـ`backend/academy_data.py` (order: 0) لكن `mobile/src/academy.ts` (القائمة
   الاحتياطية عند فشل الشبكة) لا تتضمنها بعد — مزامنة القائمتين تسدّ فجوة "لا محتوى للمبتدئ المطلق"
   المذكورة بقسم التدقيق أعلاه، بلا أي عمل هيكلي، خلال دقائق.

**✅ تعارض تقارير VotePanel — محلول بتحقّق مباشر (2026-09-16 مساءً)**: قراءة `VotePanel.tsx` كاملاً +

## الخطوات المؤجَّلة لما بعد الإطلاق (خطر أعلى/قيمة أقل إلحاحاً الآن)

نقل الملفات الفعلي لمجلدات `modules/*` (Step 1 بكل تقرير أعلاه)، تفعيل سجل المؤشرات الفعلي بدل
union ثابت، تقسيم Routers الفعلي بالباك-إند، ونقل الألواح الثمانية فعلياً لسجل tools-panels — كل هذه
خطوات آمنة نظرياً لكنها تحتاج تحديث نقاط استيراد بعدة ملفات مستهلِكة، فيُفضَّل تنفيذها بعد استقرار
الإطلاق الأول، تفادياً لأي مخاطرة غير ضرورية بالأسبوعين الحرجين.
